## Wohin die Reise geht

> **Der rote Faden dieses Abschlusskapitels:** *Wie wächst ein eingebettetes
> System über einen einzelnen Bare-Metal-Kern hinaus?*

Das Semester ist einen klaren Weg gegangen — von der Frage *wie funktioniert ein
Controller* zu *wie strukturiere ich Software darauf*:

```ascii
 8-Bit AVR      →   32-Bit Cortex-M   →   RTOS            →   HIER
 (Kap. 2-5)         (Kap. 6)              (Kap. 7-9)          (Kap. 12)

 ein Kern,          mehr Speicher,        mehrere Tasks       mehrere KERNE,
 Super-Loop,        Interrupt-NVIC,       auf EINEM Kern,     Funk & KI auf
 _delay_ms()        HAL/Register          Scheduler           EINEM Chip
```

Der ESP32-S3 ist der konkrete Anker, an dem drei Entwicklungen zusammenkommen,
die den heutigen Embedded-Alltag prägen:

1. **Mehr als ein Kern** — echte parallele Ausführung statt nur Task-Wechsel
   (FreeRTOS-SMP, Vorgriff aus [Kapitel 9](09_FreeRTOS.md#freertos-smp-auf-dem-esp32-s3)).
2. **KI auf dem Mikrocontroller** — Vektorbefehle machen neuronale Netze auf
   einem 240-MHz-Chip praktikabel (TinyML).
3. **Konnektivität als Grundeigenschaft** — Wi-Fi/BLE ist nicht Zusatz, sondern
   Teil des Systementwurfs (und bringt eigene Echtzeit-Konflikte mit).

Am Ende steht die Frage, die jede Plattformentscheidung im Feld beantworten muss:
**MCU, RTOS, Multicore oder gleich Linux — wann was?**

## Architekturvergleich: Xtensa LX7 vs. Cortex-M4

Der ESP32-S3 nutzt **nicht** einen ARM-Kern, sondern Tensilicas **Xtensa LX7**.
Für die Softwareentwicklung ist der Unterschied meist unsichtbar (FreeRTOS-API,
C/C++ identisch) — aber ein paar Architekturmerkmale prägen das Verhalten:

| Aspekt              | Cortex-M4 (STM32F4, Kap. 6)         | Xtensa LX7 (ESP32-S3)                       |
| ------------------- | ----------------------------------- | ------------------------------------------- |
| Architekturtyp      | ARMv7-M, feste Registersätze        | konfigurierbare RISC-Architektur            |
| Register            | 16 Kernregister                     | **Registerfenster** (schnelle Funktionsaufrufe) |
| Kerne               | 1 (Single-Core)                     | **2** (Dual-Core, SMP-fähig)                |
| Takt                | bis 84–180 MHz                      | bis **240 MHz** pro Kern                    |
| FPU                 | Single-Precision                    | Single-Precision + **Vektor-Erweiterung (PIE)** |
| Speicher            | Flash + SRAM on-chip                | SRAM on-chip + **externes PSRAM/Flash über Cache** |
| Debug               | SWD/JTAG (Kap. 10)                  | JTAG (integriert über USB)                  |

**Zwei Punkte, die im Alltag auffallen:**

- **Registerfenster statt fixem Registersatz.** Xtensa blendet bei einem
  Funktionsaufruf ein neues Fenster von Registern ein, statt sie auf den Stack zu
  retten. Das macht Aufrufe billig — kostet aber beim *Kontextwechsel* (FreeRTOS
  muss mehr Zustand sichern als beim Cortex-M).

- **Speicher über Cache.** Anders als der AVR (alles on-chip) oder der kleine
  Cortex-M lagert der ESP32-S3 Code und Daten teils in externes Flash/PSRAM aus,
  das über einen **Cache** angebunden ist. Konsequenz: Ausführungszeiten sind
  nicht mehr strikt deterministisch (Cache-Hit vs. -Miss) — ein wichtiger
  Unterschied zur harten Echtzeit des AVR.

> **Merke:** „Mehr Leistung" erkauft man sich mit *weniger Determinismus*. Der
> AVR taktet jede Instruktion vorhersagbar; der ESP32-S3 ist um Größenordnungen
> schneller, aber Cache und Funk-Koexistenz machen Worst-Case-Timing-Analysen
> schwerer. Für harte Echtzeit bleibt der kleine Kern oft die *ehrlichere* Wahl.

## Dual-Core & SMP

Bis Kapitel 9 hieß Multitasking: *ein* Kern, der schnell zwischen Tasks
umschaltet. Der ESP32-S3 hat **zwei physische Kerne** (PRO_CPU = Core 0,
APP_CPU = Core 1) — Tasks laufen jetzt **echt gleichzeitig**. FreeRTOS läuft hier
im **SMP-Modus** (Symmetric Multi-Processing).

### Tasks an Kerne binden

```c
// Task fest an Core 1 binden (z. B. zeitkritische Regelung, ungestört von Funk)
xTaskCreatePinnedToCore(
    controlTask,      // Task-Funktion
    "Control",        // Name
    4096,             // Stackgröße (Bytes! nicht Worte wie beim AVR)
    NULL,             // Parameter
    5,                // Priorität
    NULL,             // Task-Handle
    1);               // <-- Core-ID: 1 = APP_CPU

// Task an Core 0 binden (Wi-Fi/BLE-Stack läuft ohnehin dort)
xTaskCreatePinnedToCore(commsTask, "Comms", 4096, NULL, 3, NULL, 0);

// Scheduler frei wählen lassen (tskNO_AFFINITY)
xTaskCreate(flexTask, "Flex", 4096, NULL, 2, NULL);
```

**Das typische Muster** — und der Grund, warum Core-Bindung überhaupt wichtig ist:

```ascii
   Core 0 (PRO_CPU)                     Core 1 (APP_CPU)
  ┌─────────────────────┐             ┌─────────────────────┐
  │ Wi-Fi / BLE-Stack   │             │ Sensor-Regelung     │
  │ MQTT, OTA-Updates   │             │ (zeitkritisch,      │
  │ TCP/IP              │             │  10-ms-Takt)        │
  │ — darf "ruckeln"    │             │ — MUSS pünktlich    │
  └─────────────────────┘             └─────────────────────┘
    unregelmäßige Last                  ungestört, isoliert
```

Der Funk-Stack ist last-intensiv und unregelmäßig. Läge die Regelung auf
demselben Kern, würde ihr Timing unter jedem Wi-Fi-Burst leiden. Durch **Pinning
auf getrennte Kerne** bleibt die Regelung ungestört — das ist die Kern-Idee des
Musters „Core 0 = Kommunikation, Core 1 = Echtzeit".

### Der Preis der Parallelität: echte Race Conditions

Auf einem Single-Core-RTOS konnte man kritische Abschnitte durch *Interrupts
sperren* schützen (vgl. Kap. 9). Auf zwei Kernen reicht das **nicht mehr** — der
andere Kern läuft weiter, auch wenn dieser die Interrupts sperrt. Man braucht
einen **Spinlock**:

```c
// Spinlock schützt gemeinsame Daten über BEIDE Kerne hinweg
static portMUX_TYPE datenMux = portMUX_INITIALIZER_UNLOCKED;

void schreibe_messwert(int16_t wert) {
    taskENTER_CRITICAL(&datenMux);   // sperrt gegen den ANDEREN Kern
    gemeinsamer_puffer[index++] = wert;
    taskEXIT_CRITICAL(&datenMux);
}
```

> **Merke:** Der Sprung von einem Kern auf zwei ist kein „doppelt so schnell",
> sondern ein **qualitativer** Wechsel: Nebenläufigkeit wird *echt*.
> Interrupts-Sperren schützt nur den eigenen Kern; für kernübergreifende Daten
> braucht es einen Spinlock (`portMUX_TYPE`). Genau die Race Conditions aus
> Kapitel 9 werden hier real — nur ohne die Abkürzung „kurz die ISR sperren".

### SMP vs. AMP — zwei Wege, mehrere Kerne zu nutzen

Der ESP32-S3 macht **SMP**: *ein* Betriebssystem (FreeRTOS) verwaltet *beide*
gleichartigen Kerne. Es gibt aber eine zweite Welt — **AMP** (Asymmetric
Multi-Processing): *verschiedene* Kerne mit *verschiedenen* Betriebssystemen.

```ascii
  SMP (ESP32-S3)                      AMP (z. B. STM32MP1, i.MX)
  ┌───────────────────────┐          ┌─────────────────────────────┐
  │      FreeRTOS         │          │  Linux       │  RTOS        │
  │  ┌────────┬────────┐  │          │  ┌─────────┐ │ ┌──────────┐ │
  │  │ Core 0 │ Core 1 │  │          │  │Cortex-A │ │ │Cortex-M  │ │
  │  │ gleich │ gleich │  │          │  │ GHz,MMU │ │ │ echt-zeit│ │ 
  │  └────────┴────────┘  │          │  └─────────┘ │ └──────────┘ │
  │  ein OS, zwei Kerne   │          │  zwei OS, geteilte HW       │
  └───────────────────────┘          └─────────────────────────────┘
                                     
                                     
```

- **SMP:** gleichartige Kerne, ein Scheduler entscheidet, wo ein Task läuft.
  Einfach zu programmieren (dieselbe FreeRTOS-API), aber alle Kerne teilen das
  Echtzeit-/Nicht-Echtzeit-Schicksal desselben Kernels.
- **AMP:** Ein „großer" Kern fährt **Linux** (GUI, Netzwerk, Dateisystem —
  Kap. für Kap. mehr Komfort, aber *keine* harte Echtzeit), ein „kleiner" Kern
  fährt ein **RTOS** für die harte Echtzeit. Beide kommunizieren über
  gemeinsamen Speicher (z. B. OpenAMP/RPMsg).

> **Einordnung:** AMP ist die Antwort auf *„Ich brauche beides — Linux-Komfort
> UND harte Echtzeit"*. Man trennt die Welten physisch auf verschiedene Kerne,
> statt zu versuchen, einem einzigen OS beides abzuverlangen. Der ESP32-S3
> braucht das nicht, weil beide Kerne gleich sind und Funk ohnehin nur *weiche*
> Echtzeit ist.

## Vektor-Erweiterungen & TinyML

Warum kann ein 240-MHz-Chip neuronale Netze rechnen? Wegen der **PIE**
(Processor Instruction Extensions) des ESP32-S3 — SIMD-artige Vektorbefehle, die
mehrere Multiplikationen/Additionen *pro Takt* ausführen. Genau das braucht ein
neuronales Netz: massenhaft Multiply-Accumulate-Operationen (MAC).

```ascii
  Skalar (klassisch)              Vektor / SIMD (PIE)
  a[0]*b[0]  → 1 Takt             a[0..3] * b[0..3]  → 1 Takt
  a[1]*b[1]  → 1 Takt             (vier MACs gleichzeitig)
  a[2]*b[2]  → 1 Takt
  a[3]*b[3]  → 1 Takt             → ~4× Durchsatz bei Faltung/Matrixprodukt
```

### TinyML — der Workflow vom Modell zum Chip

**TinyML** heißt: ein (kleines) neuronales Netz läuft *auf* dem Mikrocontroller,
nicht in der Cloud. Der übliche Weg mit **TensorFlow Lite for Microcontrollers**:

```ascii
  1. TRAINIEREN        2. QUANTISIEREN      3. KONVERTIEREN      4. EINBETTEN
  ┌────────────┐       ┌────────────┐       ┌────────────┐      ┌────────────┐
  │ Keras/TF   │  ───▶ │ float32 →  │  ───▶ │ .tflite →  │ ───▶ │ C-Array im │
  │ am PC/GPU  │       │ int8       │       │ C-Array    │      │ Flash, TFLM│
  │ (groß)     │       │ (4× kleiner│       │ (xxd -i)   │      │ Runtime    │
  └────────────┘       │  , schnell)│       └────────────┘      └────────────┘
                       └────────────┘
```

Der entscheidende Schritt ist **Quantisierung**: `float32`-Gewichte werden zu
`int8`. Das Modell wird ~4× kleiner *und* die int8-MACs laufen auf der
PIE-Vektoreinheit — beides zusammen macht Inferenz auf dem Chip erst möglich.

```c
// Skizze: TFLite-Micro-Inferenz (stark vereinfacht)
#include "tensorflow/lite/micro/micro_interpreter.h"
#include "modell_data.h"          // das quantisierte Netz als C-Array

// Interpreter mit statischem Arena-Speicher (KEIN malloc auf dem MCU!)
constexpr int kArenaSize = 20 * 1024;
static uint8_t tensor_arena[kArenaSize];

void inferenz(const int8_t* eingabe) {
    // ... Interpreter aus modell_data + tensor_arena aufbauen ...
    // Eingabe in input-Tensor kopieren
    interpreter->Invoke();        // <-- hier laufen die PIE-Vektorbefehle
    // Ergebnis aus output-Tensor lesen (z. B. erkannte Geste)
}
```

**Typische Anwendungen** auf genau dieser Klasse Hardware:

- **Keyword Spotting** — „Hey Sirius" lokal erkennen, ohne Audio in die Cloud zu
  streamen (Datenschutz, Latenz, Offline-Fähigkeit).
- **Gestenerkennung** aus Beschleunigungssensor-Daten.
- **Anomalie-Erkennung** an Maschinen (Vibration/Strom) — Predictive Maintenance.

> **Merke:** TinyML ist kein „kleines Cloud-KI", sondern eine eigene Disziplin:
> Das Netz muss *von vornherein* so klein und quantisiert entworfen werden, dass
> es in KB an RAM und die MAC-Leistung des Chips passt. Der limitierende Faktor
> ist selten die Rechenzeit, sondern der **Speicher** (Arena + Modell).

## Konnektivität als Systemeigenschaft

Beim AVR war Kommunikation eine *Peripherie* (UART, I²C — Kap. 4). Beim ESP32-S3
ist **Funk Teil der Systemarchitektur**: Der Wi-Fi/BLE-Stack läuft als eigene
FreeRTOS-Tasks (fest auf Core 0), belegt RAM, erzeugt Interrupts und — kritisch —
**konkurriert mit den Echtzeit-Tasks um Zeit**.

### Das Koexistenz-Problem

Wi-Fi und BLE teilen sich *ein* Funk-Frontend (2,4 GHz). Sie können nicht
gleichzeitig senden — ein Koexistenz-Arbiter schaltet zwischen ihnen um. Für die
Anwendung heißt das: Funk-Aktivität erzeugt **unvorhersehbare Latenz-Spitzen**.

```ascii
  Core 1: Regelung  │──10ms──│──10ms──│──10ms──│──10ms──│   pünktlich ✓
                                                              (weil isoliert)
  Core 0: Wi-Fi     │▓▓░░░░▓▓▓▓░░▓▓░░░░░▓▓▓▓▓▓░░│   Bursts, unregelmäßig
                     └─ würde die Regelung stören, LÄGE sie auf demselben Kern
```

Genau deshalb das Muster von oben: **Regelung auf Core 1, Funk auf Core 0.** Die
Core-Trennung ist hier keine Optimierung, sondern eine *Echtzeit-Notwendigkeit*.

### OTA-Updates — Firmware über Funk

Konnektivität ermöglicht **Over-the-Air-Updates**: neue Firmware ohne physischen
Zugang. Das knüpft direkt an die CI/CD-Pipeline aus
[Kapitel 10](10_Debugging_Testen_CICD.md#praxisbeispiel-push--build--test--flash)
an — der letzte Schritt „FLASH/DEPLOY" ist beim ESP32-S3 eben *drahtlos*.

Die zwei zentralen Sicherheitsmechanismen:

- **A/B-Partitionen (Dual Bank):** Das Update wird in eine *zweite*
  Flash-Partition geschrieben, während die laufende Firmware unangetastet bleibt.
  Erst nach erfolgreicher Prüfung wird umgeschaltet.
- **Rollback:** Bootet die neue Firmware nicht sauber (kein „Health-Check"-OK),
  fällt der Bootloader automatisch auf die alte Partition zurück.

```ascii
  ┌────────────┐   OTA schreibt    ┌────────────┐
  │ Partition A│   ───────────▶    │ Partition B│
  │ (läuft)    │                   │ (neue FW)  │
  └────────────┘                   └────────────┘
        │                                │
        │  Reboot in B, Health-Check     │
        │  OK?  ── ja ──▶ B wird aktiv   │
        │       ── nein ─▶ Rollback zu A │                                .
```

> **Merke:** OTA ohne Rollback ist ein Risiko, kein Feature — ein fehlerhaftes
> Update würde ein Gerät im Feld unerreichbar machen („bricken"). A/B-Partitionen
> + Health-Check + automatischer Rollback sind der Standard, der das verhindert.

## Einordnung & Ausblick: Wann welche Plattform?

Der ESP32-S3 ist eine Antwort — nicht *die* Antwort. Das Semester hat vier
Plattformklassen berührt; die Wahl richtet sich nach **Echtzeit-Härte**,
**Rechenlast**, **Konnektivität** und **Determinismus**:

| Kriterium              | 8-Bit AVR       | Cortex-M + RTOS   | ESP32-S3 (SMP)      | Linux (AMP/MPU)      |
| ---------------------- | --------------- | ----------------- | ------------------- | -------------------- |
| Beispiel               | ATmega328       | STM32F4           | ESP32-S3            | STM32MP1, i.MX, RPi  |
| Harte Echtzeit         | **sehr gut**    | **sehr gut**      | mittel (Cache/Funk) | schlecht (nur RT-Patch) |
| Determinismus          | **maximal**     | hoch              | mittel              | niedrig              |
| Rechenleistung         | gering          | mittel            | **hoch** (+KI)      | **sehr hoch**        |
| Konnektivität          | extern nötig    | extern nötig      | **integriert**      | **integriert**       |
| RAM                    | KB              | 10er-KB           | 100er-KB (+PSRAM)   | **MB–GB**            |
| Betriebssystem         | keins/RTOS      | RTOS              | RTOS (SMP)          | Linux (+RTOS via AMP)|
| Typischer Einsatz      | Sensor, Aktor   | Regelung, Antrieb | IoT-Knoten, Edge-KI | Gateway, HMI, Vision |

### Die Konvergenz von MCU und MPU

Historisch waren **MCU** (Mikrocontroller: klein, deterministisch, kein OS) und
**MPU** (Mikroprozessor: groß, Linux, MMU) getrennte Welten. Sie **wachsen
zusammen**:

- Von *unten*: MCUs wie der ESP32-S3 bekommen Multicore, KI-Beschleuniger, Funk,
  MB-großes PSRAM — Dinge, die früher MPU-Territorium waren.
- Von *oben*: MPU-SoCs (STM32MP1) integrieren einen **Cortex-M-Echtzeitkern
  neben** dem Linux-Cortex-A — AMP bringt die Echtzeit-MCU *in* die MPU.

```ascii
   früher:   [ MCU ]         Lücke          [ MPU/Linux ]
                                             
   heute:    [ MCU ]──ESP32-S3──▶ ◀──STM32MP1──[ MPU/Linux ]
             klein          Konvergenzzone         groß
                     (Multicore, KI, Funk, AMP)
```

### RISC-V im ESP32-Universum

Espressif setzt zunehmend auf **RISC-V** statt Xtensa: Der **ESP32-C3** (single
core RISC-V) und **ESP32-C6** (RISC-V + Wi-Fi 6 + Thread/Matter) zeigen die
Richtung. Für die Softwareentwicklung ändert sich wenig (FreeRTOS, ESP-IDF
bleiben) — aber die **offene ISA** RISC-V löst proprietäre Kerne zunehmend ab,
gerade im unteren und mittleren Leistungsbereich.

> **Der Bogen des Semesters:** Wir sind vom 8-Bit-AVR mit `_delay_ms()` bis zum
> Dual-Core-Chip mit neuronalem Netz und Wi-Fi gekommen. Die *Konzepte* aber —
> Interrupts, Scheduling, Nebenläufigkeit, Fehlertoleranz, Debugging — sind
> dieselben geblieben; sie skalieren nur mit. Genau deshalb war der Weg über die
> „kleinen" Controller kein Umweg, sondern das Fundament: Wer Race Conditions auf
> dem AVR verstanden hat, versteht sie auf zwei ESP32-Kernen erst recht.

## Zusammenfassung & Aufgaben

**Kernaussagen:**

- Der ESP32-S3 (Xtensa LX7, Dual-Core, 240 MHz, PIE-Vektoren, Wi-Fi/BLE)
  vereint Multicore, Edge-KI und Konnektivität auf *einem* Chip.
- **SMP** (ein OS, gleiche Kerne) macht Nebenläufigkeit *echt* — Interrupts
  sperren reicht nicht mehr, es braucht **Spinlocks** für kernübergreifende Daten.
- Das Muster **Core 0 = Funk, Core 1 = Echtzeit** ist eine Echtzeit-Notwendigkeit,
  keine Optimierung (Koexistenz-Latenz).
- **TinyML** wird durch Vektorbefehle + int8-Quantisierung praktikabel; der
  Engpass ist der Speicher, nicht die Rechenzeit.
- **OTA** braucht A/B-Partitionen + Rollback, um Geräte im Feld nicht zu bricken.
- Die Plattformwahl ist ein Kompromiss zwischen **Echtzeit/Determinismus**
  (spricht für kleine Kerne) und **Rechenleistung/Konnektivität** (spricht für
  ESP32/Linux). **AMP** verbindet beide Welten physisch.

**Aufgaben zum Nachdenken:**

> **1)** Eine Drohne braucht (a) eine 1-kHz-Lageregelung und (b) einen Video-Stream
> per Wi-Fi. Auf welchen Kern(en) des ESP32-S3 platzieren Sie was — und warum?
> Wo wäre eine AMP-Plattform (Linux + Cortex-M) die bessere Wahl?
>
> **2)** Warum genügt auf dem ESP32-S3 das aus Kapitel 9 bekannte „Interrupts
> sperren" *nicht* mehr, um einen gemeinsamen Zähler zu schützen? Was passiert
> konkret, wenn beide Kerne ihn gleichzeitig inkrementieren?
>
> **3)** Ein TinyML-Modell ist als `float32` 200 KB groß und passt nicht in den
> RAM. Welche zwei Effekte hat die int8-Quantisierung — und warum hilft sie
> *doppelt* (Speicher *und* Geschwindigkeit)?
>
> **4)** Ordnen Sie die vier Plattformklassen (AVR, Cortex-M+RTOS, ESP32-S3,
> Linux) den folgenden Produkten zu und begründen Sie: Herzschrittmacher,
> smarte Türklingel mit Kamera, Waschmaschinen-Timer, Industrie-Gateway.
